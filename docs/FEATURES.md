# Lumos - Feature Status

Status values: **done** · **in-progress** · **planned** · **idea**

Ordered like the checklist in [`TODO.md`](TODO.md): what is still planned or only an idea first,
then what is in progress, then what is done.

## Planned and ideas

| Feature | Status | Notes |
|---|---|---|
| Link enrichment | idea | Summaries and key points from links |
| Docs explainers | idea | Steppable SVG explanations rendered at build time into the docs - how a message becomes a note, what an MCP tool call touches - from a scene that also renders as text for an agent. Planned as Phase 10; the engine ([lantern](https://github.com/ivarvong/lantern), MIT, zero runtime dependencies) is not on npm, so it arrives pinned or vendored, and a spike measures its compiled size before anything is committed to it. Nothing enters an app bundle ([explainers.md](explainers.md)) |
| A note's story, step by step | idea | An **Explain** panel walking through a note or a graph cluster: what it links to, what shares its tags, what it is not connected to - the narration the graph cannot give, and the same scene answerable as text over MCP. Gated on the docs slice, because it would put a second rendering model beside the canvas graph |
| The vault format, taken apart | idea | A scene that decomposes `2026-10-26-plan-the-week.md` into date, slug and extension and then lights up the frontmatter fields - taught where people get it wrong, rendered into the docs |

**Not planned:** before/after explainers of a code change, which is what lantern was built for.
Lumos stores notes, not history, so there is no diff to explain; that is recorded in
[explainers.md](explainers.md) so the idea is not re-opened from the library's title alone.

## Done

| Feature | Notes |
|---|---|
| Profile | The avatar at the top of the sidebar opens the profile (`?view=profile`): the name and one line the vault gives itself, up to six pinned notes as cards (folder, date, opening lines, tags - each opening, each unpinned from the card), the year's calendar with one square per day and absolute amber bands, a year picker over every year holding a note, and the current streak, longest run, active days and busiest day counted from each note's creation date. The bands are absolute rather than scaled to the peak, so a vault of one-note days is not painted as brightly as a busy one. The name, line and pins are preferences in `localStorage`, not files in the vault; everything else is computed from the listing the shell already has, so the pane opens with no request and works with the daemon stopped (`@lumos/vault-utils/profile`, `src/lib/profile.ts`, `src/components/ProfileView.tsx`) |
| Vault insights | The **Stats** tab counts the vault and shows where it is thin: notes, folders, distinct tags, resolved links and unresolved targets, notes added this week and this month, the notes with the most links pointing in, the notes with no links and no tags, the commonest tags and the size of each folder (`?view=insights`). Every row acts - a note opens, a tag filters the list with the chips' own handler, a folder looks at that folder the way the sidebar does - and the whole pane is computed from the listing and the graph the shell already holds, so it opens with no request and works with the daemon stopped. When `GET /graph` did not answer, `linksKnown` is false and the pane says those figures are missing rather than printing zeros (`@lumos/vault-utils/insights`, `src/components/InsightsView.test.tsx`; the same function answers the MCP server's `vault_health`) |
| MCP server | `apps/mcp` puts the vault in front of Claude Code, Claude Desktop and any other MCP client: thirteen tools over stdio - `vault_health` (the vault counted: links, unresolved targets, what arrived this week, the notes nothing links to, tags and folder sizes), `list_folders`, `list_notes`, `search_notes`, `read_note`, `create_note`, `update_note`, `rename_note`, `move_note`, `delete_note`, `list_trash`, `restore_note`, `create_folder`. Notes are addressed by key (`Folder/name.md`), a refusal is answered as a tool error carrying the vault's own sentence, and every write goes through `@lumos/vault-utils`, so a note an agent writes is stamped `source: mcp` and is otherwise an ordinary note. `LUMOS_VAULT` picks the vault; the default is this repository's. See [mcp.md](mcp.md) |
| Config file | `lumos.config.json` for the vault path, port, allowlist, the WhatsApp switch and the two Ollama settings, with the environment overriding it. A missing file means the defaults; a bad one stops the daemon with one sentence naming the setting |
| WhatsApp capture | Baileys multi-device, allowlist, auto-reconnect. The link is reported and driven from the app: the status bar chip names its state and opens a panel with the sentence, the pairing code and one button (`GET /whatsapp`, `POST /whatsapp/connect`, `POST /whatsapp/disconnect`, `bridge.ts` + `createWhatsAppBridge()` in the daemon, `WhatsAppPanel.tsx` in the desktop) |
| Command parsing | `/idea`, `/interview`, `/goal`, `/read`, `/plan`, `/find`, `/newfolder`, `/help`, a bare `/` for the menu, and `/<folder>` for any folder the vault has |
| Any folder | A folder is a directory, so folders are not a fixed list: `/newfolder Movies` makes one and `/movies <link>` files into it from then on, and **+ New folder** in the sidebar does the same from the desktop. The sidebar, the composer, the move menus and the graph legend all read that one list (`POST /folders`, `listFolderNames()` in `@lumos/vault-utils`) |
| Folder rename & remove | A folder can be renamed (`/renamefolder Movies\|Film`, or **Rename** in the sidebar, `PATCH /folder`) and removed (`/delfolder Movies`, or **Delete**, `DELETE /folder`). The rename is one directory rename on disk - every note inside keeps its filename, date and bytes - and the links that named the old folder are rewritten in the notes that carried them; the remove moves the notes to Inbox and then drops the empty directory, so removing a folder never takes a note with it. Files that are not notes are left in place and the folder is kept (`renameFolder()`/`removeFolderNotes()` in `@lumos/vault-utils`, `Sidebar.tsx`) |
| The `/` menu | WhatsApp has no command autocomplete for a chat, so one keystroke asks for it: a bare `/` answers with one line per folder and the rest of the commands, built from the folders on disk so a folder made a minute ago is in it (`helpText()` in `handler.ts`) |
| `/plan` | `/plan today` or `tomorrow` replies with at most five short points from the local Ollama model, over the vault's 20 newest notes and the machine's own date. An empty vault answers without a request; Ollama stopped, a timeout, a missing model, a bad status or an unreadable answer each reply with one actionable sentence. `ollamaUrl`/`ollamaModel` in the config file (`OLLAMA_URL`/`OLLAMA_MODEL` in the environment), defaulting to `http://127.0.0.1:11434` and `llama3.2:3b` (`plan.ts` in the daemon) |
| Typed routing | The pane and the open note *are* the address: TanStack Router's one route at `/` carries `?view=notes|graph|trash` and `?note=Folder/name.md` as typed, validated search parameters. A reload, the back button and a pasted link all land on the same place, an unknown view value falls back to the notes pane, and a delete drops the deleted note's parameter (`router.tsx` in the desktop, `App.routing.test.tsx`) |
| Zustand vault store | The daemon read (with the demo fallback), the re-read after every save or file operation, and the list's filters live in one zustand store (`src/lib/store.ts`). A failed re-read throws instead of speaking for itself, so the caller turns it into the status-bar notice. The pane and the open note stay in the address from the router, and session-only UI state (notices, drafts, pane widths) stays in the component (`store.test.ts`) |
| Bulk operations | A checkbox per row chooses several notes; a bulk bar then offers move (a folder picker), add-tag, archive (the note's existing `status: archived` - the vault gained no new concept) and clear. Every write is settled on its own, so a refusal on one note never abandons the rest, and the status bar says what landed plus the first refusal in the daemon's own words. The selection is dropped when leaving the notes pane (`lib/bulk.ts`, `App.bulk.test.tsx`) |
| Subtle transitions | A pane switched to (notes, graph, trash), the search palette, the bulk bar and a status-bar notice each enter with one short fade or slide-down (`index.css`), so a switch reads as a change of place rather than a jump. Every keyframe sits behind `prefers-reduced-motion: no-preference`, so a system asking for less motion gets none |
| List virtualization | Above 50 notes the list windows itself through `@tanstack/react-virtual`: only the rows on screen plus a small overscan are in the DOM, each measuring itself as it renders, so a keystroke in the search above no longer re-renders every row. Below the threshold nothing changed - the rows are exactly as they were (`VIRTUALIZE_ABOVE` in `NoteList.tsx`)
| Vault writer | Markdown + YAML frontmatter, slugified filenames |
| HTTP API | `POST /message`, `GET /health`, `GET /stats` (the vault counted), `GET /qrcode` (the pairing page), `GET /whatsapp` plus `POST /whatsapp/connect` and `/whatsapp/disconnect` for the capture link, the six read-API routes in the row below, `PUT /note` for saving an edited body, `POST /notes` for creating one, `PATCH /note`, `POST /note/move` and `DELETE /note` for renaming, moving and deleting a note, and `POST /folders`, `PATCH /folder` and `DELETE /folder` for making, renaming and removing a folder |
| Link expansion | `GET /link` reads title/description/og:image and the readable text of a page, for `/read` and `/interview` links. A PDF link is read the same way - its text through the same card, titled by its file name - and a file served without a useful content type is judged by its bytes rather than refused (`fetch-link.ts` + `read-pdf.ts` in the daemon, `unpdf` for the parsing) |
| In-app playback | A YouTube or Vimeo link plays in the note viewer (no-cookie embed), an image link renders as the image; neither needs the daemon |
| Social embeds | An Instagram post, reel or IGTV link and a Facebook video, reel or post render in place through the host's own embed, classified from the URL alone. The caption, site and lead image come from the daemon's `/link` when it is running, so the embed plays with the daemon stopped and only loses its caption |
| Embed frames | `LinkMedia.frame` picks the box: 16:9 for a video, portrait for an Instagram permalink, a taller card for a Facebook post that keeps its caption and reaction counts |
| Page reader | The scraped text of a link, capped at 6,000 characters, rendered as text with a loading, error and retry state. The site's chrome is stripped first: chrome elements, `<pre>` code samples, a repeated line, a bare bracketed label and `data-` payloads all stay out. An Instagram or Facebook permalink has no readable body (a JavaScript shell), so those show the embed and its metadata instead of an empty reader |
| Link safety | `GET /link` refuses non-http(s) URLs, credentials in the URL, and anything local — including a redirect into a private address — with time, redirect and size caps |
| `/find` search | Searches title, tags and body; replies with up to five matches and counts the rest |
| Tag extraction | `#hashtags` in a captured message become the note's frontmatter tags (lower-cased, de-duplicated), read by `extractTags()` - the same function the graph builds tag nodes with - so the tags in the file and the tag nodes in the graph cannot disagree |
| Shared packages | `@lumos/shared` types + `@lumos/vault-utils` (parse/list/search/write) |
| Vault listing/search | `listNotes`, `getNotesByFolder`, `searchNotes`, `readNote` |
| Frontmatter validation | `validateFrontmatter()` checks `created`, `tags`, `source` and `url` and reports one reason per broken field; a note with a broken block is still listed and readable, and the viewer shows the reasons above the body (`validateFrontmatter()` in `@lumos/vault-utils`, unit-tested) |
| Vault graph | `extractLinks`/`extractTags`/`buildGraphFromNotes`/`neighborhood` in `@lumos/vault-utils` (`./graph` subpath, browser-safe) |
| Link parsing | `parseLinkMedia`/`extractPreview`/`firstExternalLink` in `@lumos/vault-utils` (`./link` subpath, browser-safe) |
| Daemon read API | `GET /notes`, `/notes/search`, `/folders`, `/note`, `/graph` + CORS |
| Dark UI theme | Tailwind v4 tokens, near-black background |
| Resizable panes | A `separator` between list and viewer: drag, double-click to reset, `←`/`→`/`Home` from the keyboard, 240-560px and kept while the Graph tab is open (`src/lib/pane-size.ts`) |
| Desktop vault browser | Folder sidebar + note list + viewer + status bar, with tag filtering |
| Tag filtering | The tags in the current folder and query become chips with counts; a chip, or a tag on a note card, narrows the list. A tag node in the graph offers **Show notes** with the same filter (`src/lib/filter.ts`, unit-tested) |

Only the body is written — the frontmatter block survives character for character — and the listing, folder counts and graph are re-read afterwards, with a status-bar notice if that refresh fails (`src/components/NoteEditor.tsx`) |
| Editor preview | The editor's right half renders the draft as it is typed, through the same `Markdown` component the reader uses, so a table that does not parse or a fence that swallows the note shows up before the save. **Hide preview** / **Preview** toggles it (`aria-pressed`), the panes scroll independently, an empty draft says so, and the panes stack below the `md` breakpoint (`src/components/Markdown.tsx`, `src/components/NoteEditor.tsx`) |
| Note creation | **New** opens a composer in the list's own pane: a folder picker and a textarea, filed through `POST /notes` with `Cmd/Ctrl+Enter`. It uses the capture writer, so the first line is the title and `#hashtags` become tags, and the note is stamped `source: desktop`. The folder starts where the list is looking. A failed create keeps the draft (`src/components/NoteComposer.tsx`) |
| Tags and status | The strip under the note header edits what the body cannot carry: each tag is a chip with a remove button, **Add a tag** takes a new one, and a **Status** picker offers `new`, `active`, `done` and `archived`. The daemon cleans a tag the way the graph reads one (no `#`, lower-case, de-duplicated) and writes only the frontmatter block, so the body is byte-identical afterwards; a block that does not parse is refused rather than replaced (`PATCH /note/meta`, `updateNoteMeta()` in `@lumos/vault-utils`) |
| Note file operations | The **...** button in the note header opens **Rename**, **Move** and **Delete** (`src/components/NoteActions.tsx`). Rename rewrites the filename (keeping its date prefix) and the body's first heading together, then carries the links in other notes that pointed at the old title, keeping each link's shape; move keeps the filename and only changes the folder; delete asks first and moves the file into the vault's `.trash`, with **Undo** in the status bar until the notice is dismissed (`restoreNote()` puts it back, refusing a name that has been taken again). A target name another note holds is a `409` and nothing is replaced, a refusal keeps the panel open with the daemon's sentence, and the listing, folder counts and graph are re-read afterwards (`renameNote()`/`moveNote()`/`deleteNote()`, plus `linkResolver()`/`rewriteLinks()` in `@lumos/vault-utils`) |
| Trash | The **Trash** tab in the sidebar lists what a delete kept, newest first, each entry with its folder and when it went (`GET /trash`). **Restore** puts one back under the name it had and opens it, refusing a name taken in the meantime and keeping the entry when it does. **Empty the trash** takes two presses because it is the one action with no undo in the app, then removes every entry for good (`DELETE /trash`) and closes the panel; a refusal keeps it open with the daemon's sentence. Emptying drops the edges those notes held in the graph rather than resurrecting a note to keep a link tidy (`src/components/TrashPanel.tsx`, `listTrash()`/`emptyTrash()` in `@lumos/vault-utils`) |
| Safe writes | The path is checked against the vault root before anything is read, and the note is written to a temporary name then renamed over itself, so an interrupted save cannot truncate it (`replaceNoteBody()`, `updateNote()` in `@lumos/vault-utils`) |

| Live capture | A note captured on WhatsApp appears in an open window without a reload, because the link's own read carries `lastAt` - when a message was last answered - and a change there pulls the vault and diffs the listing.
